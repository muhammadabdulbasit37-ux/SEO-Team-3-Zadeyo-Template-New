# Repository conversion rules

This is the **CHEATS FOR THE ISLE** master template at **https://cheatsfortheisle.com/** for independently branded game-cheat sites. Convert only a clone identified by the owner. Setup, template maintenance and audits do not authorize a new-game conversion. Preserve existing work outside the task.

- Read [docs/architecture.md](docs/architecture.md) for source ownership, routes, commands and hosting, and [docs/template-defects.md](docs/template-defects.md) before treating existing behavior as correct. Defects are follow-up work, not invariants to reproduce.
- Those documents include historical MW4 values. Verify current facts from source; consult [docs/forum-restoration.md](docs/forum-restoration.md), [docs/reviews-list-update.md](docs/reviews-list-update.md) and the active `content/manifest.json` for subsequent changes. Preserve legitimate history, provenance, aliases, licenses and third-party endpoints rather than blindly replacing old names.
- [docs/conversion.example.json](docs/conversion.example.json) is an intake example, not runtime configuration. Copy it for an authorized conversion and fill it with confirmed business facts.
- Use the [repo-local skills](docs/skills.md) from `.agents/skills/`. Read only the skills relevant to the current stage. These workflows travel with the clone. Repository and owner rules take precedence over generic skill advice.
- This file's owner-supplied community-content policy supersedes older instructions in docs, examples or skills to generate forum starters or request only business facts. Tool support for generated discussions is not authorization to use it. The mandatory research workflow below also takes precedence over older instructions that would finalize targets from a small query sample alone.

## Four-prompt workflow

1. [Convert the clone](docs/prompts/01-convert.md). Verify intake and sources, research SEO, plan and implement the game-specific site and four locales. Save the intake, native run path, completed work and pending dependencies in ignored `.content/handoff.md`. Finish independent work while waiting for owner content.
2. [Import forum threads](docs/prompts/02-import-forum.md). Resume the saved run and import the owner's records. When the full pack is valid, complete installation and any integration held by the forum gate.
3. [Import customer reviews](docs/prompts/03-import-reviews.md). Import the owner's records into the native archive and product review sections. Verify rendered text, attribution and counts.
4. [Audit and optimize](docs/prompts/04-final-audit.md). Verify and repair the complete built site and give a release-readiness decision with evidence. Resume the same clone and intake throughout.

In Prompt 1, use `site-architecture` for the game-specific page and link map and `copywriting` for new site-owned prose. Use `copy-editing` after the factual draft and during Prompt 4 as needed. Use `web-design-guidelines` for the rendered visual review in Prompt 4. Keep forum and review imports exact. Use the native research, content, link graph and QA procedures for SEO evidence and release checks.

## Intake, sources and public brand

Use `support@<canonical hostname>` if email is blank, report the fallback, and distinguish configuration from mailbox verification. Derive the game from the supplied identity and product reference. Use the optional Keyword Pack for title/meta guidance and independently research uncovered routes and locales. With no pack, research titles and meta descriptions. - The required Main Product Reference URL is the sole source of main-product features, prices, plans and durations. If access is blocked, ask for the owner's main-product summary and record it as the substitute evidence. Preserve source and date provenance. Keep unconfirmed facts pending. Never inherit those values from the prior game's product or use a search snippet, competitor or referral destination to fill gaps.
- Keep each clone publicly branded as its own site. Omit Zadeyo and affiliate-disclosure copy from public pages, navigation, legal/support copy, metadata, structured data, feeds and public-facing assets. Keep the product reference in private intake/provenance and use internal product or support pages for public guidance. Keep supplied referral destinations in checkout routing and its generated noindex fallback. The destination can appear in the browser once the shopper leaves through checkout. Do not claim to be the publisher, developer, payment processor or provider of a service the site does not perform.
- Use only the four owner-supplied referral URLs as checkout destinations. Keep branded, unprefixed `/go/` links, checkout link qualification and approved query/plan behavior. Never derive a checkout URL from a reference URL or use an inherited referral to fill a blank. Missing essentials block only dependent work and release readiness. Follow the [intake and review procedure](docs/seo/seo-research-workflow.md#intake-keyword-authority-and-review-boundaries).

## Permanent conversion policy

- Preserve the four-product system and give each product distinct reader intent. The main product uses the supplied name and sourced facts. For HWID Spoofer, Skin Changer and UGC, preserve the template's names, plans, prices, durations, facts and media. Rewrite their wording and update routing to the supplied referrals. Utility summaries and references are not required.
- Rewrite all game-specific commercial and editorial copy: homepage, product descriptions/features, utility descriptions, FAQs, headings, metadata, articles and supporting pages. Name/keyword substitution alone is insufficient. Preserve content depth, useful structure and commercial purpose; remove repetitive filler, generic AI phrasing and keyword stuffing.
- Write as our website and products: “Our cheats include…” when supported, rather than “The seller offers…”. Keep language professional, confident and conversion-focused. Never invent capabilities, compatibility, prices, detection status, guarantees, customer experiences or evidence. Keep unknown facts unresolved and request essential inputs.
- Assign distinct search intents to URLs instead of targeting the same primary query everywhere. Editorial topics must help explain product features, compatibility, requirements, troubleshooting, selection or purchasing; exclude unrelated news, walkthroughs and entertainment. Link useful editorial content naturally to the appropriate main or utility product.
- Preserve the color theme, typography, layout patterns, navigation structure, responsive behavior and visual quality. Adapt authorized game-specific branding, imagery and SEO within the established design system. Preserve the favicon unless replacement is explicitly requested; do not redesign without permission.
- Preserve utility functionality and checkout behavior. Do not infer target-game compatibility from a utility's existence or historical community reports.

## Mandatory conversion sequence

Every authorized future website conversion must follow this sequence. First inspect the template, verified business inputs, existing URLs and links. Detailed requirements are in the mandatory [SEO research strategy](docs/seo/seo-research-workflow.md) and [internal linking strategy](docs/seo/internal-linking-workflow.md); their sections support this single sequence rather than defining alternative workflows.

1. Research the target game and competitors.
2. Perform comprehensive keyword research.
3. Create keyword clusters and keyword-to-page mapping.
4. Plan the website's topical architecture, hubs and site-wide internal links.
5. Write genuinely unique, search-intent-focused content.
6. Implement extensive, relevant contextual internal linking.
7. Optimize technical SEO and localization across all four languages.
8. Audit the complete internal link graph, including every intended indexable route.
9. Run production builds, tests and SEO validators against the final implementation.
10. Fix identified issues, rerun affected checks and report final results with evidence and remaining limitations.

Step 8 requires current generated HTML: build as needed for analysis, then complete final verification in step 9. Repeat graph analysis after link/content changes. Conversion completion requires both strategies and final-state evidence; documentation/audit work alone does not trigger a conversion.

## Mandatory internal linking

- Apply the linked internal linking strategy throughout planning, implementation and verification. Repeat affected link optimization whenever adding an article, including opportunities in older relevant pages.
- Plan contextual links by topic and reader intent across categories. For substantial guides, investigate roughly **10–20 placements** and use the ones that earn their place. Give priority to the relevant product, hub, guide or FAQ for the reader's next step. Review both directions and revisit older related pages whenever adding a guide.
- Place the most useful next-step link at the first natural passage, even if it appears mid-article. Use concise, destination-accurate anchors. Avoid redundant destinations, forced exact matches and clutter near hero, pricing and checkout controls.
- Require crawlable incoming links for every intended indexable page and homepage reachability; investigate underlinked pages using both total and contextual incoming links. Use real `<a href>` links, current canonical destinations and the correct locale via routing helpers. Exclude redirects/non-indexable utilities from coverage targets, while preserving legitimate checkout, legal and language-switch links. Never alter supplied forum/review text to insert links; use relevant site-controlled surrounding elements only.
- Reuse existing route inventories, parser and validators for local production-output graph analysis; extend tooling where useful during conversions. Separate deterministic errors from semantic recommendations and human review. Do not inject links with global replacements or add unnecessary libraries/services. Record measured incoming/outgoing counts, orphan/broken/underlinked findings, implemented changes, exceptions and remaining opportunities in the required records. Do not claim automation or ranking/engagement improvements without evidence.

## Verification and prohibited side effects

- Inspect scripts before execution. `npm ci` installs the lockfile; `npm run dev` serves source; `npm start` serves `dist` on port 4173 by default. `npm run preview` is Astro preview, not evidence of Worker parity.
- Choose checks appropriate to the change. For application/conversion changes, verification order is `npm run typecheck`, `npm run build`, `npm test`, `npm run validate`, then `npm run validate:runtime`. Documentation-only edits may use focused consistency/diff checks and relevant existing tests without rebuilding unchanged application output. Report exactly what ran and unresolved failures; never claim unrun checks passed.
- `typecheck` uses Astro's checker; plain `tsc` cannot check Astro imports. Ignored `.content/` drafts are excluded. No lint script exists. `test:local-hosts` is available; historical MW4-specific `part15-verify.mjs` is not The Isle or future-conversion acceptance criteria.
- Build optimizes gameplay variants and rewrites tracked generated public files before building/postprocessing `dist`. Review `git diff` afterward and preserve pre-existing edits. Validation policy is `src/config/validation.ts`; Astro writes `.astro/validation-config.json` from source. `validate` rejects stale output and checks locally without contacting external services; see [docs/validation.md](docs/validation.md).
- For a Cloudflare Pages release, run `npm run validate:pages` against the final production build. `validate:browser` uses installed Chrome (or `QA_BROWSER_CHANNEL`) and intercepted checkout. `validate:cloudflare` is the separate Workers check and its build hook rebuilds output. Local checks do not certify dashboard configuration, deployed behavior, checkout fulfillment or live SEO.
- **Do not commit, push, deploy, change DNS or submit URLs to IndexNow/other indexing services automatically. The owner handles Git and deployment.** These actions require an explicit task instruction; conversion, audit and validation requests do not authorize them. Do not make real purchases or contact partner checkout during ordinary tests.
- Ordinary `npm run build` never deploys or submits URLs, even with `INDEXNOW_KEY`. `npm run indexnow:submit` and `npx wrangler deploy` require separate authorization.

Keep permanent repository rules here, architecture and verification procedures under `docs/`, and shared skill instructions under `.agents/skills/`.
